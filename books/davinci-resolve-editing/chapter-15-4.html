Chapter Fifteen, Section Four

Crashes, Corruption, and Recovery

Part XV of XVI
Category Practical
Sheet 090 / 095
Depends On 15.3
Read Time ~7 Min

Chapter 15.3 dealt with a broken connection between a timeline and its media. This chapter deals with something more alarming: the project itself failing to open, or closing unexpectedly mid-session. It's worth saying up front that this is the least common category of the three Chapter 15.1 defined, and also the one editors tend to panic about most — largely because it's the one most people understand least about how Resolve actually stores a project in the first place.

Crashes and Corruption Are Different Problems

A crash is transient: Resolve closes unexpectedly, usually from a specific action overloading memory, a GPU driver fault, or a plugin misbehaving, and reopening the application afterward typically finds the project exactly as it was. Corruption is different and more serious: the project's own saved data has become internally inconsistent, and the project may fail to open, open with entire sections missing, or behave unpredictably even after a clean relaunch. Treating a crash like corruption leads to unnecessary panic; treating corruption like a simple crash leads to wasted time reopening a file that was never going to open cleanly.

Resolve's Project Database, Not a Flat File

Unlike many editing tools, a Resolve project isn't a single file living on disk in the way a document from other software might be. It lives inside a project database — local by default, or shared, as Chapter 2.1 first described when explaining what a project actually is — which changes what "corruption" even means here. A damaged database can affect one project among many sharing it, or in rarer cases the database itself, and understanding this structure is what makes the difference between panicking over one broken project and correctly recognizing that every other project in the same database is very likely still fine.

Live Save and Automatic Backups

Resolve continuously writes project changes to its database as you work, rather than relying solely on a manual save at the end of a session, and it additionally keeps periodic project backups by default. This combination is the main reason catastrophic data loss from a crash is rarer in practice than editors moving from other tools tend to expect — the record of a session usually exists somewhere, either in the live database state or in a recent automatic backup, well before any manual save was ever triggered.

Most crashes cost nothing but a restart. Real corruption is rarer than it feels in the moment — and Resolve's database structure, understood correctly, usually means the damage is contained to far less than the whole project.

When a Project Won't Open

The practical recovery sequence, in order: first, simply relaunching Resolve and reopening the project, since a genuine crash frequently resolves this way with nothing lost. If that fails, checking for a recent automatic project backup and restoring from it, accepting the small amount of work done since that backup as the actual cost of the failure. If neither works, exporting or restoring at the database level rather than the individual project level is the next step, since the fault may sit in the database's own integrity rather than in any one project's content.

Distinguishing Corrupted Media From a Corrupted Project

It's worth applying Chapter 15.1's triage directly here: a project that opens fine but shows a specific clip failing to play or displaying visible artifacts is very likely a media problem, not a project one, and belongs back in Chapter 15.3's relinking territory rather than anything covered in this chapter. Genuine project corruption is broader than a single clip — missing timelines, an interface that won't load correctly, settings reverted en masse — and that breadth is itself a useful diagnostic signal.

The Habit That Actually Prevents This

Everything in this chapter assumes a backup exists somewhere to fall back on, which makes Chapter 2.8's case for deliberate, regular project archiving the real prevention here, not any recovery technique. A project database that's never been backed up outside Resolve's own automatic system is one bad disk failure away from a loss no recovery step in this chapter can undo — the discipline that actually matters happens well before a crash, not during the recovery from one.

Crashes are usually recoverable with nothing more than a restart, and even real corruption is rarely as total as it first appears once the database structure behind it is understood. Chapter 15.5 closes this part by stepping back from acute failures entirely, to the smaller, everyday mistakes that cause most of the trouble editors run into in the first place — and how to avoid needing this chapter's advice at all.

Key Concepts to Remember

  • A crash is transient and usually resolves on relaunch; corruption is a lasting fault in the project's saved data — different problems, different responses.
  • Resolve stores projects inside a database rather than a single flat file, which limits how far a given fault typically spreads.
  • Live save and automatic project backups mean a full session is rarely lost outright, even after a hard crash.
  • A single misbehaving clip in an otherwise healthy project points back to Chapter 15.3's relinking, not to genuine project corruption.
