Chapter Twelve, Section One

Why Resolve Was Built for Teams, Not Just Editors

Part XII of XVI
Category Foundational
Sheet 072 / 095
Depends On 11.6
Read Time ~6 Min

Chapter 11.6 closed Part XI on a bounded problem: handing a finished project off to one other person, cleanly enough that nothing breaks when it lands on their system. That's a real skill, but it assumes a specific shape — one project, one handoff, one recipient, with the two periods of work never overlapping. This chapter opens Part XII by removing that assumption entirely. What happens once a project isn't handed off at all, but worked on by several people at the same time — an editor cutting scenes, a colorist grading the ones already locked, a sound mixer laying in temp music, an assistant still ingesting new footage — all inside the same project, simultaneously, for weeks on end?

A Harder Problem Than Handoff

Handoff, as Chapter 11.6 covered it, is fundamentally a serial problem: one person finishes a stretch of work, then another person begins, and the two periods of activity never actually overlap. Simultaneous, team-based editing is a different category of problem entirely — several people changing the same underlying project at the same moment, where each person's changes need to become visible to everyone else without silently overwriting somebody else's work, and without anyone unknowingly working from a copy that's already gone stale. That's concurrency, not sequencing, and it is a meaningfully harder problem to solve well than handoff ever was.

Why Most Editing Software Treats This as an Afterthought

A great deal of editing software, at its core, treats a project as a single file sitting on a disk — something one person opens, works inside, and saves, with exclusive access baked into the format itself. Multi-editor situations, in that world, get handled around the software rather than by it: splitting a show into reels assigned to different people, exporting and re-importing XML or EDL files between separate project copies, manually merging changes back together at the end of a session. It works, in the sense that professionals have been doing it for decades. It also adds real coordination overhead and real room for mistakes — two people quietly working on the same reel, unaware, being the classic failure this kind of workaround never fully closes off.

A Project That Was Never Really a File

Chapter 2.1 established early in this book what a Resolve project actually is: not a flat document on disk in the way a word processor's file is, but an entry inside a database, with the Media Pool, timelines, bins, and settings all stored as structured records rather than as one serialized blob. That's true even in the simplest single-user setup. It's a structural choice, present in the software from early on, shaped by Resolve's lineage in high-end color-grading suites — environments where a colorist, an assistant, and often a client in the room were already expected to interact with the same live session. That foundation is what makes genuine multi-seat, concurrent work structurally possible in Resolve, rather than a workaround stitched on top of a format that was never built to share.

Seven Pages, Occupied at Once

Chapter 1.2 introduced Resolve's seven pages as specialized workstations, each built around one stage of the post-production process, all operating on the same underlying project. That idea extends further than it first appears to. Nothing about the page structure requires only one of those workstations to be occupied at a time. An editor can be actively building structure on the Edit page while a colorist is already grading scenes that have locked, while a sound mixer is laying temp music into Fairlight, before the cut as a whole is finished — all inside one project, at the same moment. Once the mechanics behind that are in place, which the rest of this part covers, that overlap is the normal shape of professional work, not an exception to it.

A project file that only one person can open at a time is a structure built around a single editor, with everything about team-based work bolted on after the fact. A shared database, built for concurrent access from the start, is a genuinely different foundation — not a faster version of the same idea, but a different one.

What the Rest of This Part Covers

The remainder of Part XII builds this idea out from concept to daily practice. Chapter 12.2 gets technical about the mechanism itself — Collaboration Mode and the shared project database that makes concurrent access real rather than theoretical. Chapter 12.3 turns practical, covering bin locking and the concrete habits that keep several people from colliding inside the same project. Chapter 12.4 extends the same ideas across distance, into remote grading and review workflows. Chapter 12.5 closes the part by looking at how editorial, color, and sound teams actually coordinate across all of it, in practice, on a real production.

Key Concepts to Remember

  • Handoff is a serial problem, solved once; simultaneous team editing is a concurrency problem, solved continuously — the two require genuinely different tooling.
  • Software built around a single project file treats team access as a workaround; Resolve's database foundation treats it as structurally native instead.
  • A Resolve project is a database entry, not a flat file — a choice shaped by the software's roots in shared grading-suite sessions.
  • The seven pages from Chapter 1.2 can be occupied simultaneously by different specialists on one project — the normal shape of professional team work, not an exception to it.
