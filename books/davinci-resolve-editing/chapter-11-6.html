Chapter Eleven, Section Six

Handing Off a Project to Someone Else

Part XI of XVI
Category Practical
Sheet 071 / 095
Depends On 11.5
Read Time ~7 Min

Every chapter in Part XI so far has assumed the deliverable is a finished video file, headed to a viewer, a broadcaster, or a platform. This closing chapter covers a genuinely different kind of delivery: handing the project itself — editable, unfinished in the sense that someone else needs to keep working on it — to another person entirely. It's a rarer need than a standard render, but a real one, and it fails in ways rendering a file never does.

A File Isn't a Project

The distinction is worth stating plainly, because it's easy to conflate the two once Part XI's rendering work feels routine. A rendered deliverable, from Chapter 11.5, is a fixed, finished result — nothing about it is meant to change further, and nothing about it needs the receiving party to have Resolve at all. A project handoff is the opposite: the receiving editor needs to keep editing, grading, or compositing, which means they need the actual timeline, bins, and settings intact and workable, not a flattened result of what those things once produced.

What a Clean Handoff Actually Requires

Media management is the first real concern, and the most common point of failure. Every piece of media the project references — footage, graphics, Fusion elements from Part X, audio — needs to travel with the project or be reachable at a path the receiving system can actually resolve, or the handoff arrives broken regardless of how clean the timeline itself is. Consolidating and collapsing media into a self-contained package, and explicitly checking for anything that comes up as offline or unlinked before sending anything, is the difference between a handoff that opens working and one that opens to a wall of missing-media warnings.

A rendered file only has to look right once, to whoever's watching it. A handed-off project has to actually work — every reference resolved, every piece of media reachable — the moment someone else opens it.

Interchange Formats: Leaving Resolve Entirely

When the receiving editor isn't working in Resolve at all, the project itself doesn't transfer — only a translated version of its structure does, through an interchange format like XML, AAF, or EDL. These formats carry timeline structure, edit points, and often basic metadata across to a different NLE, but they don't carry everything: Fusion compositions, node-based grades, and application-specific effects generally don't survive the translation intact, since the receiving software has no equivalent structure to receive them into. Knowing this in advance changes what a handoff should actually include — often a rendered, composited, and graded version of the trickiest sections alongside the editable timeline, so the receiving editor isn't left trying to reconstruct Part IX or Part X's work from scratch in an unfamiliar tool.

Staying Inside Resolve: Full Project Transfer

When the receiving editor is also working in Resolve, a full project or database export preserves considerably more — timelines, bins, node-based grades, and Fusion compositions largely intact, since the receiving software genuinely understands the same structures the sending project used. This is the cleaner handoff by a wide margin whenever it's available, and it's worth treating "does the other side use Resolve" as one of the first practical questions in any real handoff, since the answer changes what actually needs to be prepared.

Notes and Documentation: The Non-Technical Half

The cleanest media management and the right interchange format still leave a real gap a receiving editor has to close alone without some documentation: which LUTs were used and where they came from, any naming conventions the bin structure assumes, render notes on what's already been delivered versus what's still outstanding. This is a small, easy step to skip under deadline pressure, and one of the most common reasons a technically clean handoff still costs the receiving editor real time reconstructing context that a few written notes would have preserved directly.

Key Concepts to Remember

  • A project handoff needs a working, editable structure — a different goal from a rendered file, which only needs to look right once.
  • Clean media management, with nothing offline or unlinked, is the single most common point of failure in a project handoff.
  • Interchange formats like XML, AAF, and EDL carry timeline structure across to other software, but not Fusion compositions or node-based grades.
  • Written notes on LUTs, naming, and delivery status close a gap that clean media and the right format alone don't cover.
