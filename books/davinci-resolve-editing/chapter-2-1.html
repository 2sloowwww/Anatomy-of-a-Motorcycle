Chapter Two, Section One

What a Project Actually Is

Part II of XVI
Category Foundational
Sheet 007 / 095
Depends On 1.6
Read Time ~8 Min

Chapter 1.6 mentioned, in passing, that a Resolve project isn't a single file the way a Word document or a Photoshop file is. This chapter stops to actually explain what that means, because it changes how you should think about saving, backing up, and organizing your work — and getting it wrong is one of the more disorienting experiences a new editor coming from file-based software can have with Resolve.

A Project Is a Record in a Database, Not a File on a Drive

When you create a project in Resolve, you're not choosing a location on disk to save a file to. You're creating a new record inside a project database — by default, a local database Resolve creates and manages for you the first time you launch it, though Part XII covers how that database can also live on a shared server for team collaboration. Everything about your project — the Media Pool's bin structure, every timeline, every clip's metadata and color grade, your render settings — lives as data inside that database record, not as a standalone file you can find in Finder or Explorer and double-click.

This is the single biggest adjustment for editors coming from file-based NLEs, where a project genuinely is a file, and "backing up the project" means copying that file somewhere safe. In Resolve, there's no single file to copy for that purpose — which sounds alarming until you understand what replaces it. Chapter 2.8 covers the actual backup and archiving tools built around this database model; this chapter's job is just to make the model itself clear first.

Resolve doesn't have a "Save" button in the way most software does, and that's not an oversight. There's nothing external to save to — your project already lives, continuously, inside the database as you work.

Why There's No "Save" Button the Way You'd Expect

Resolve does have a Save command, and it's worth using deliberately at meaningful points — but it doesn't behave like saving a document. Because your project already exists as a live record in the database, most of your changes are already being tracked as you make them. Save, in this context, is closer to committing a clean checkpoint than it is to "writing the file to disk for the first time." Auto-save and auto-project-backup features, covered in Chapter 2.8, exist specifically because Resolve assumes continuous work against a live database, not periodic writes to a static file.

This also explains a related question new editors often have: "where is my project file, so I can copy it to a USB drive and take it home?" There usually isn't a simple answer to that question in the way it's being asked, because the project isn't a portable file sitting somewhere waiting to be copied. If you need a portable, standalone version of your project — to move between machines that don't share a database, to send to a collaborator, or to archive outside Resolve entirely — you export one deliberately, as a `.drp` file, which Chapter 2.8 covers as part of the backup and archiving workflow.

What a Project References, Versus What It Contains

It's worth being precise about what actually lives inside that database record, because it's a smaller set of things than beginners often assume. The project contains your Media Pool's organization, your timelines, your metadata, your grades, your render settings — the structure and instructions built on top of your footage. It does not contain the footage itself. This is the same pointer-based idea from Chapter 1.1, just scaled up from "a timeline points at footage" to "a project points at footage."

That means a project is only as good as its ability to find the media files it references. Move your camera footage to a different drive, rename a folder in the path, or open the project on a machine where that drive isn't connected, and Resolve will report that media offline — not because anything about your edit was lost, but because the pointers can no longer resolve to real files. Chapter 2.3 covers organizing footage in a way that keeps this risk low, and relinking — the process of telling Resolve where moved media has gone — comes up again in Part XV when we cover conform and relink issues in more depth.

Duplicating a Project as a Practical Safety Habit

Because there's no single file to simply copy as a backup, Resolve gives you an equivalent inside the Project Manager: duplicating a project. This creates a full, independent copy of the database record — Media Pool, timelines, grades, everything — under a new name, at whatever point you choose to do it. Many editors use this as a lightweight version-control habit: duplicate the project before a risky structural change, before a client review, or at the end of each working day, so that older states of the work remain available even if something goes wrong in a later session.

This isn't a replacement for the archiving tools in Chapter 2.8, which handle long-term, portable backups including the media itself. But as a fast, in-the-moment safety net during active work, duplicating a project inside the database takes seconds and costs almost nothing, which makes it worth building into your regular habits rather than treating as a special occasion.

Carrying This Forward Into the Media Pool

With the project itself understood as a database record that organizes and points at footage rather than contains it, the next question is exactly how that organization works day to day — which is where the Media Pool comes in. Chapter 2.2 picks up immediately from here, looking at bins as the actual organizational unit inside a project, and why they behave differently from the folders you're used to on your operating system.

Key Concepts to Remember

  • A Resolve project is a record inside a managed database, not a standalone file — there's no single file to double-click or drag onto a USB drive.
  • Save behaves like a checkpoint against a continuously live database, not like writing a file to disk for the first time.
  • A project points at footage rather than containing it — moving or renaming media files after the fact is what causes "media offline" errors.
  • Duplicating a project inside the Project Manager is a fast, low-cost safety habit — a lightweight alternative to full archiving for everyday checkpoints.
